# THREATS.md: Threat Model, Mitigations, and Accepted Risks

This document enumerates the security, concurrency, and integrity threats analyzed for **LedgerLine**, the architectural defenses implemented, the specific tests verifying each defense, and knowingly accepted risks.

---

## Threat Matrix

| **1** | **Race Overdraft / Double Debit**<br>Concurrent withdrawal requests exploiting race conditions to overdraft account balance into negative values. | Explicit row-level lock ordering via `SELECT ... ## Analysis of Open & Accepted Risks (Rows 16 and 22)

### Row 16: Denial of Service via Audit Connection Saturation
* **Risk:** Each denied access attempt (e.g. attempting to debit an unowned account) opens a separate autocommit connection to write into `audit_logs` before raising `404 Not Found`. A high-frequency distributed attacker could flood the API with invalid account requests to consume connection pooler slots.
* **Why Accepted for Challenge Scope:** 
  1. Preserving audit trails across transaction rollbacks without an external message broker (Kafka/RabbitMQ) requires an independent database transaction.
  2. Neon AWS connection pooler (`pgbouncer`) handles thousands of idle and brief transactions.
  3. Production hardening recommendation: Deploy an ingress rate limiter (Cloudflare Turnstile or Redis token bucket) to throttle requests per IP before reaching the application layer.

### Row 22: Account ID Existence Enumeration via Transfer Probing
* **Risk:** A registered user can discover whether account ID `X` exists by attempting a transfer of 1 paisa: if ID `X` does not exist, the API returns `404 Not Found`; if it exists, the transfer succeeds with `201 Created`.
* **Why Accepted for Challenge Scope:**
  1. Financial transfer systems must allow crediting an existing account without requiring prior relationship between sender and recipient.
  2. The response strictly conceals the recipient user's email, name, and account balance (only returning the transferred amount and the sender's updated balance).
  3. Production hardening recommendation: Replace integer auto-increment account numbers with opaque UUIDv4 or public IBAN/Virtual Payment Addresses (VPAs).
